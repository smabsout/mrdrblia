## Project Overview

**Context:** This is a personal price-guide and cataloging tool for my own murderabilia collection — not a public marketplace or commercial platform. It's used to track items I own, log comparable sales I've researched, and get a data-grounded sense of value. Keep this framing in mind for any UX copy (e.g. "My Collection" rather than storefront language).

Build a full-stack price-guide web application (Phase 1 MVP — no marketplace, no payments). The core feature is an item catalog with a **comp-based valuation engine** that computes defensible, traceable price estimates from historical sale data. AI is used in this build (see "AI Layer" section below) for description normalization and comp-matching — but never to generate the price number itself, which stays rule-based and auditable back to specific sale records.

**Stack:**
- Frontend: React + TypeScript + Vite + Tailwind CSS + shadcn/ui
- Backend: Node.js + Express + TypeScript
- Database: PostgreSQL + Drizzle ORM
- Charts: Recharts
- Auth: session-based (email/password only for MVP — use Lucia or a simple express-session + bcrypt setup)
- Optional AI layer: OpenAI/Anthropic API for description normalization and similarity matching ONLY (never for generating the price number itself)

## Valuation Engine — Exact Logic

Implement this as a standalone, unit-testable module (`server/valuation.ts`), NOT inline in route handlers. This is the core IP of the product — build it carefully.

### Step 1: Classify item into a notoriety/comp tier

```
Tier A = at least 2 verified sales exist for THIS EXACT item OR near-identical
         reissues/duplicates of it (e.g. multiple prints of the same signed photo)
Tier B = fewer than 2 direct sales, but comp_matches exist with similarity_score >= 0.75
         against items with verified sales
Tier C = no direct sales and no qualifying comps
```

Tier is computed at valuation time, not stored statically on the item — it changes as new sales are entered.

### Step 2: Gather the sale set

- **Tier A:** all `verified = true` sales where `item_id = this item` (or explicitly linked duplicate items)
- **Tier B:** all `verified = true` sales from items in `comp_matches` where `similarity_score >= 0.75`, sorted by similarity descending, capped at top 10 comps
- **Tier C:** no sale set — do not compute a numeric estimate. Show category-level range only (see Step 5).

### Step 3: Apply recency weighting (exponential decay)

For each sale, compute weight:

```
weight = 0.5 ^ (days_since_sale / half_life_days)
```

- `half_life_days = 180` (6 months) as the default constant — expose as a config value, not a magic number buried in code
- A sale from today has weight 1.0; a sale from 6 months ago has weight 0.5; 12 months ago has weight 0.25; etc.

### Step 4: Apply condition/authentication segmentation

Do NOT average across condition tiers or authentication status — this produces misleading numbers.

- Group sales by `condition_grade` + `authentication_status` combination
- Within the item's detail page, show separate estimate bands per combination that has at least 1 sale (e.g. "Authenticated / Excellent: $X–$Y" and "Unauthenticated / Good: $A–$B" as separate rows)
- If the item being valued has a known `authenticator` field, prioritize/highlight the matching segment first

### Step 5: Compute the estimate

For each segment with n ≥ 1 sales:

```
weighted_median = weighted_median(sale_prices, weights)
low_estimate  = weighted_percentile(sale_prices, weights, 0.10)
high_estimate = weighted_percentile(sale_prices, weights, 0.90)
```

If n = 1 for a segment: show that single sale price as a reference point, explicitly labeled "1 sale on record — not a statistical estimate," not as a low/median/high band.

For Tier C items: no price computed. Display: "No comparable sales data. Category range for [category]: $X–$Y based on N unrelated sales" — pulled from a simple category-wide (not item-specific) query, clearly separated visually from item-level estimates.

### Step 6: Confidence label

```
sample_size >= 8  -> 'high'
sample_size 3-7   -> 'medium'
sample_size 1-2   -> 'low'
sample_size 0     -> no confidence label, show Tier C messaging instead
```

### Step 7: Caching

- Recompute and write to `valuation_cache` whenever a `sales` row is inserted/updated/verified for that item, or nightly via cron for comp-based (Tier B) items whose comps changed
- Item detail page reads from `valuation_cache`, not live computation, for page-load speed
- Always show `computed_at` timestamp on the frontend so users know data freshness

### Auditability requirement

Every number shown on the frontend must be clickable/expandable to show the exact sale records that produced it (date, price, source, condition). This is non-negotiable for this category — an unexplainable number is a liability. Build the "show your work" UI panel as part of the item detail page, not as a stretch feature.

### Step 8: Gain/loss calculation (collection tracking)

Since this tracks a personal collection, compute and display alongside the valuation bands:

```
unrealized_gain_loss = median_estimate - purchase_price
unrealized_gain_loss_pct = (unrealized_gain_loss / purchase_price) * 100
```

- Show this per-item on the item detail page and as a portfolio-level total on a new **Collection Dashboard** page (see Pages section)
- If `median_estimate` is unavailable (Tier C, no comps), show purchase price only with "current value unknown" rather than a fabricated gain/loss
- Dashboard should show: total spent (`sum(purchase_price)` across owned items), total estimated current value (`sum(median_estimate)` where available), and net unrealized gain/loss

## AI Layer (included in this build — build after the core engine works)

Use an LLM API call for these two functions, each isolated in its own server module:

**1. `normalizeItemDescription(rawText: string)`**
- Input: messy admin-entered free text
- Output: structured JSON `{ itemType, associatedCase, approxDate, materialType, notableFeatures[] }`
- Prompt the model to return ONLY valid JSON, no prose. Validate/parse defensively (try/catch, schema check with zod) before writing to DB.

**2. `computeSimilarity(itemA, itemB)`**
- Generate text embeddings (via an embeddings endpoint) from a concatenation of `name + category + subcategory + source_event + normalized description`
- Store embeddings, compute cosine similarity offline in a batch job, write results into `comp_matches`
- This runs as a nightly job over newly added/edited items — not on every page load

Do NOT let either function touch `sale_price`, `low_estimate`, `median_estimate`, or `high_estimate` fields. If you're tempted to add "AI suggested price" anywhere, don't — flag it in a code comment as explicitly out of scope for MVP.

## AI Chat Agent: "Morbid"

Add a conversational chat agent named **Morbid**, accessible from a persistent chat panel/drawer available on every page. Morbid is framed as a true-crime and murderabilia domain expert the user can talk to about their collection.

### Backend

- New route: `POST /api/morbid/chat` — accepts `{ message: string, conversationId?: string }`, returns streamed or full text response
- New table `morbid_conversations`: `id, user_id FK, created_at`
- New table `morbid_messages`: `id, conversation_id FK, role ('user'|'assistant'), content, created_at`
- Call the LLM API (Anthropic or OpenAI) server-side only — never expose the API key to the frontend
- On each request, give Morbid relevant context by injecting a compact summary of the user's collection (item names, categories, purchase price, current valuation, notoriety tier) into the system prompt or as retrieved context, so it can answer questions like "what's my most valuable piece" or "tell me about the case behind [item]" without hallucinating details about items it doesn't have data on

### System prompt (starting point — refine as needed)

```
You are Morbid, a knowledgeable true-crime and murderabilia expert helping the user
understand and manage their personal collection. You have access to their catalogued
items, purchase prices, and computed valuations.

Your role:
- Answer questions about specific criminal cases, historical context, and notoriety
  factors relevant to items in the collection, using only well-established, publicly
  documented facts. When you're not certain of a detail, say so rather than inventing it.
- Help the user understand WHY an item might be valued the way it is (notoriety of the
  case, rarity, authentication status, condition) — but always defer to the app's
  computed valuation numbers rather than inventing your own price estimate. If asked
  for a price, restate the app's computed low/median/high band and cite the underlying
  sale count, don't generate a new number.
- Help surface patterns in the user's collection (e.g. "you have three items tied to
  cases from the same decade").
- Decline to help with anything about acquiring items from active/ongoing criminal
  cases, contacting incarcerated individuals for solicitation purposes, or anything
  that could constitute harassment of victims or victims' families.
- Do not glorify perpetrators or minimize harm to victims — keep discussion factual
  and contextual, not sensationalized.

You are not a licensed appraiser and should say so if the user asks for a formal
appraisal — recommend a professional authenticator/appraiser for anything with real
transaction stakes.
```

### Frontend

- Chat drawer component (slide-out panel, similar to a support-chat widget) with message history, streaming text display
- Conversation persists per user (load `morbid_messages` on open)
- Optional: quick-action buttons like "Summarize my collection" or "What's changed in value since I last checked?" that pre-fill common prompts

### Guardrail

Morbid must never output a numeric price estimate of its own — it can only reference and explain numbers already computed by the valuation engine (Steps 1–8 above). Enforce this in the system prompt AND, if feasible, with a lightweight regex/parsing check on the response before displaying it, flagging any dollar-amount pattern that doesn't match a number already present in the injected collection context.

## Pages to Build

1. **Collection Dashboard** (`/`) — home page. Shows all owned items in a grid, plus portfolio totals (total spent, total estimated value, net gain/loss per Step 8). This replaces a public storefront view since this is a personal collection tracker.
2. **Item Detail** (`/items/:slug`) — photos, description, provenance, purchase price/date, valuation bands (per Step 4 segmentation), gain/loss, price history table, expandable "show your work" panel
3. **Add/Edit Item** (`/items/new`, `/items/:id/edit`) — form matching the `items` schema (including purchase price/date/source), triggers `normalizeItemDescription` on save
4. **Add Sale/Comp Record** (`/items/:id/sales/new`) — form matching `sales` schema for logging comparable sales you've researched, `verified` checkbox, triggers valuation recompute on save
5. **Verification Queue** (`/sales/pending`) — list of unverified sale/comp records to confirm before they count toward valuation
6. **Auth** (`/login`, `/register`) — basic email/password (single-user is fine for MVP, but keep auth so the data isn't wide open if deployed)
7. **Morbid Chat** — persistent chat drawer available from every page (see "AI Chat Agent: Morbid" section)

## Explicit Guardrails (do not violate these while building)

- Never auto-generate a `sale_price`, `low_estimate`, `median_estimate`, or `high_estimate` value via LLM — these are computed only from the formulas in Steps 3–5
- Never mark a `sales` row `verified = true` automatically — this is an admin-only manual action
- Never scrape external sites for sale data — all `sales` rows are manually entered via the admin form
- Every estimate shown must link back to underlying sale records (Step 7 auditability requirement)
- Items default to `status = 'pending'` and are not publicly visible until an admin approves them
